# Session 2026-09-03 (afternoon) — deeper analysis, honest partial

## What I tried

Attempted to close COMMDRV.EXE 10/10 by disassembling the main
decompressor (0x1e52a, 801 bytes) and tracing its calls. Read the full
disassembly and looked for chunking mechanisms.

## What I found

**Main decompressor structure:**
- Outer loop reads FILE data in 0x7800 (30720) byte chunks via fread
- Calls `mid_func` (0xeb70) which turned out to be Watcom C's fwrite wrapper
- Calls near helpers at 0xd128 (3x), 0xd330, 0xe4ac (2x), 0xbb6e
- No direct access to the `[0xc4c] / [0xc4e]` globals we thought were the
  "kick_char state"

**kick_char / f_ram / flushram are probably NOT the LHA I/O layer:**
- kick_char has ZERO callers in the binary
- f_ram is called ONCE, conditionally, from 0x23de2 when a check equals 0x1700
- The 459-byte data at [0xa80] appears to be executable code under DS=0x2d91 —
  the actual DS at f_ram call time is unresolved and probably different

These functions likely belong to the **installer's hardware/disk layer**
(installer writing files to disk with format-specific handling), NOT the
LHA decompressor. This was a red herring across multiple sessions.

**No 4KB (0x1000) constant anywhere:**
- Searched main + all helpers for immediate 0x1000, 0x0FFF, 0xF000
- Zero hits
- Only 0x0100 (256) appears twice in helper_e4ac
- 0x7800 (30720) appears 4 times — outer file chunk size

## Divergence re-verified

At output byte 7398, operation 3483:
- Code decoded = 256 (min copy code)
- Expected by oracle = literal 0x26
- bio.pos=4097, bitcount=7
- 11 bits consumed for this code

The bit stream at this position (bytes 4094..4097):
```
hex : 18 db e5 82
bits: 00011000 11011011 11100101 10000010
```

Our decoder consumed bits from bit position 32758 (byte 4094, bit 6) to
32769 (byte 4097, bit 1). Those 11 bits produced Huffman code 256
according to our tree, but the CORRECT next output is literal 0x26 = 38.

## Interpretation

The 11 bits we read do produce code 256 under the Huffman tree we built
at block start. So either:
1. The Huffman tree we built is WRONG (unlikely — 9/10 files decode fine)
2. The compressor RE-INITIALIZED the tree mid-block somehow
3. There's a bit-stream marker we're missing (like "reset codes here")
4. WCSC uses per-N-code re-encoding not present in stock LHA

Option 3 or 4 fit the "WCSC has special chunking not in stock LHA"
theory best. But without seeing kick_char/f_ram/flushram actually
running (via emulator with breakpoints, or Ghidra decompile of the
correct functions), we can't identify the marker.
