ROOT NAMES THE BRANCH
---------------------
The Repo is called PCBIRC. ROOT=\OUT translates into PCBIRC\OUT. PCBIRC
is just the root directory the repo source lives in and can be name
anything. The build root needs testing for DOS/OS2 and later LINUX. The build
should be tested in Wine and Win32 before checked in dosbox-x.zip buildroot.
The mak/cfg files should contain a section that allow Make CLEAN to run and 
clean out build files and artifacts.

Clark wrote `ROOT = \PROJ` for a company with one product.  This tree is
one of four.  All eleven makefiles that declared a root now say:

    !ifndef ROOT
    ROOT     = \OUT
    !endif

ROOT already names a PCBoard branch; \PCB said it twice and named nothing.
      \PCBSRC, which appeared in two makefiles, was not Clark's and named
      nothing either. changed to \OUT

The guard is not decoration.  Borland MAKE 3.6 lets a MAKEFILE
definition beat a `-D` command-line macro -- the opposite of GNU make --
so `MAKE -DROOT=\DELTA154` silently does nothing without it.  Tested
both ways, before and after. `MAKE -DROOT=\DELTA154` needs to be changed
to branch \OUT and not branch name. Branch name has its own section.

153/PCBOARD.MAK had `ROOT = ..`, already branch-neutral by being relative and
arguably the better pattern. PPLC.MAK and USERNET2.MAK doesn't declare ROOT at
all, needs to be checked:

PCBKIT vs PCBKMS: same source, different compiler.

	Compiler	Why it exists
PCBKBC	Borland C++ 3.1	done
PCBKIT	Turbo C 2.01	
PCBKMS	Microsoft C 7.0	

A door author in 1996 used whatever compiler they owned, and object format, name
decoration and runtime conventions don't mix across vendors. So Clark shipped the
same toolkit three times. 3 compilers × 4 memory models = the 12-library matrix. 
We have 4 of 12.

What's actually different about each:

PCBKIT — Turbo C 2.01 is pre-ANSI, C only, no C++. Our headers carry //
comments and __BORLANDC__ < 0x500 guards it can't parse. Earlier work added 
compiler guards for this. Clark's own PCBKITL.LIB is 341 C symbols to 4 C++, 
which confirms it was a C-mode build. PCBKMS — the blocker is the host, not the code. 
"MSC 7.0's DOS compiler hard-requires a DPMI host; Microsoft's own README names 386MAX. 
The OS/2-hosted 16-bit add-on sidesteps DPMI entirely but needs an OS/2 host." This might
be incorrect might work without HDMI host..

"msc7.x with OS/2 addon. devtools/ and dosbox-x.zip

The components table in the same section spells out the host ×target mapping exactly:

MS-DOS hosted     OS/2 hosted      Compiler
C13216.EXE        C11616.EXE       pass 1
C1XX3216.EXE      C1XX1616.EXE     C++ pass 1
C23216.EXE        C21616.EXE       pass 2
C33216.EXE        C31616.EXE       pass 3

VMDATA WAS OFF BY ONE
---------------------
`toolkit/pwa153/SOURCE/VMFUNCS.C` is a crew reimplementation of Clark's
`VMDATA.LIB`, which this repo has never had.  It treated record indices
as zero-based.  Every caller in the tree - all of them Clark's own code -
treats them as ONE-based:

    MAKEIDX.C  266   for (X = 1; X <= PathNum;  X++)
    MAKEIDX.C  313   for (X = 1; X <= NumFiles; X++)
    SORT.C     352   for (Counter = 1; Counter <= Recs; )
    CI_BUILD.C 138   Rec = VMRecordGetByIndex(&CnamesIdxSet,i,NULL)

and all four `VMSort()` call sites pass start as 1.  So every record came
back shifted by one and the LAST record returned NULL, because the
`idx >= count` guard rejected it.  `VMSort()` made it worse by discarding
start and cnt and sorting the whole set from offset 0.

The library was corrected, not the callers - the callers are the evidence
of the contract.  Editing MAKEIDX.C, SORT.C and CI_BUILD.C to match a
reimplementation's accident was considered and rejected.

`VMSeqFinalPass()` was added.  SORT.C calls it three times and it is
declared nowhere in this repo except an `#ifdef __WATCOMC__` block in
`pcbsm_externs.h` - the only surviving evidence of its signature.

MAKEIDX.EXE had already been built, run, and recorded as good with this
bug in it.  Same lesson as below: a count is not a verification, and
neither is a clean link.

  toolkit/pwa153/H/VMDATA.H          VMSeqFinalPass declared
  toolkit/pwa153/SOURCE/VMFUNCS.C    one-based; VMSort honours start/cnt
  MAIN/build/VMDATA-RECONSTRUCTION.md

Still open: `VMDataStartUp` ignores its swap-file argument, so the whole
set must fit in the 640K real-mode heap.  PCBSM sorts only boards that
fit in memory until a paging store is written.  Seven no-ops in VMFUNCS.C
go live the day it exists.

THE COMM-DRV SOURCE IS NOT ATTIC MATERIAL
-----------------------------------------
`attic/` is for things that have been SUPERSEDED.  The nine `.386`
category libraries went there only AFTER being rebuilt and verified.
sysop/0's `pcbdcom-fossil5c.zip` is the opposite case: eleven files that
nothing supersedes and, for two of them, the only copies in existence.
All eleven land live.

  pcb1541/pcbdcom/src/    fossil.c  int14.c  commdrbl.c  libsbl.c
  pcb1541/pcbdcom/inc/    compat.h  pcbdcom.h
  pcb1541/pcbdcom/doc/    INT14-FOSSIL5C-STATUS.md  FOSSIL-OBJ-ANALYSIS.md
  pcbcbase/COMMDRV/H/     COMM.H
  toolkit/pwa153/bc31/obj/  FOSSIL.OBJ  COMMDRV.OBJ

FOSSIL.OBJ and COMMDRV.OBJ are recovered Clark originals, Oct 11 1993,
out of TOOLKIT2.ZIP -> TOOLKIT/BC/PCBKIT_L.EXE.  Their OMF records carry
`y:\modem.c`, which settles a long-standing assumption: FOSSIL.OBJ is
NOT MODEMFOS.C.  It is MODEM.C compiled `-DCOMM -DMULTIPORT -DLIB`,
which #includes MODEMFOS.C and MODEMASY.C.  COMMDRV.OBJ is the same file
with `-DCOMMDRV`, pulling in MODEMDRV.C instead.

All four of those sources are in `pcb153/SOURCE/MODEM/`, so these objects
are rebuildable - which is exactly why they stay out of the attic.  They
are the reference oracle for the rebuild: acceptance is that the new
FOSSIL.OBJ exports match the recovered one's 79 symbols.  They move to
the attic the day that test passes.

This also answers the "One is missing" note in CATEGORY-LIBRARIES.md.  A
toolkit makefile asks for `$(SDKOBJ)\toolkit\large\fossil.obj` and there
is no FOSSIL.C in the toolkit tree, because there never was one - the
object came from SOURCE\MODEM.

DRYRUN is there because del /f has no Recycle Bin.  A guarded delete is

per-directory checksum files, so:

the repo root is reported.  todo\CHECKSUMS.md is ignored - it is a dated
release note from July, not a manifest.

means every listed file is intact; it says nothing about what else is
lying around.  VERIFY now prints that in as many words when it finishes.

THE TWO WARNINGS ARE THE RESULT, NOT A DEFECT.  The source opens with

READ OUT OF THE BINARY, WITH ADDRESSES
--------------------------------------
DGROUP base is 0x5230 in the image, fixed by correlating 27 of 33 string
offsets against immediate operands in the code.

  0x3CB        reads 0xF3 = 243 bytes per record
  0x340-0x37E  2-byte header copied, write position saved, count copied
  0x3EE-0x403  cmp ax,[0xedf] then a call at 0x2DEB - BOTH must pass
  0x42F        drop message, format string at ds:0x00B4
  0x43F-0x460  tail copied in 0x400 = 1024-byte chunks
  0x462-0x47E  seek back to the saved position, write the kept count
  0x48F,0x4A1  unlink(cfg) then rename("tmp.cfg", cfg)

ds:0x00B4 is "\nremoved %5d %s..." - with a LEADING NEWLINE that a plain
strings dump hides.  That is why the earlier note quoted it without one.

------------------------------------------

    version-checks it against "15.0", and keeps the name in a DGROUP
    buffer at ds:0x10E4.  The reconstruction takes it on the command
    line instead.
  - the exact body of the second test.  The binary calls 0x2DEB with
    (conf, far ptr to ds:0x00AA) and drops on zero, then calls 0x2F75

CORRECTION SAME DAY: PACKFIDO ALSO REMOVES DUPLICATES
-----------------------------------------------------
Date: 2026-09-23.  Traced the two routines v0.4.1 had left as INFERRED,
and the first draft was wrong about what the program does.

0x2DEB, called BEFORE keeping a record:
    ax >>= 3 ; les bx,[bp+6] ; bx += ax
    al = es:[bx] ; cl = conf & 7 ; al >>= cl ; ax &= 1
  = (bitmap[conf >> 3] >> (conf & 7)) & 1

0x2F75, called AFTER keeping one, same arguments:
    dl = 1 << (conf & 7) ; not dl ; and [es:bx],dl
  = bitmap[conf >> 3] &= ~(1 << (conf & 7))

A CLEAR, NOT A SET.  The bit means "this conference is still available",
so a record is dropped for THREE reasons, not one:

  1. conference number above the count      cmp ax,[0xedf]
  2. conference does not exist              bit never set
  3. A RECORD FOR THAT CONFERENCE WAS ALREADY KEPT - the first one
     cleared the bit, so every later area for the same conference goes.
     First one wins.

So PACKFIDO removes DUPLICATE AREAS as well as orphaned ones.  That is
half of what the program is for and nothing in its strings hints at it -
"removed %5d %s..." reads the same either way.

The first draft used a range check and a seen[] map that nothing tested,
which would have kept every duplicate.  Corrected; rebuilt, 11,362 B.
The bitmap IS the program.

ALSO TRACED: 0x2D45, the existence check at the top.
    mov dx,0x1bee / ah=0x1A / int 21h     set DTA
    mov dx,[bp+4] / cx=0x17 / ah=0x4E     FindFirst, attribute mask 0x17
    al=0xFF / jc                          not found -> 0xFF
    else  al = [0x1c03]                   the file's ATTRIBUTE byte
It returns the attributes, not a yes/no.  access() is close enough for
the caller, which only tests for 0xFF, and is left as is with the real
behaviour recorded here.

STILL INFERRED, and now the only thing that is: where the bitmap is
BUILT.  It has to come from CNAMES - a bit per conference, set where the
conference exists - but that routine was not traced.  The reconstruction
sets every bit in range, which collapses test 2 into test 1 and leaves
the duplicate removal exact.

--------------------------------------------
v0.4.1 shipped a reconstruction with two routines marked INFERRED and a

PCBOARD.DAT IS A TEXT FILE
--------------------------
    *** PCBoard Version 14.5 & 15.0 data file ***
    SYSOP
    0
    -1
    110

Line-oriented, one value per line.  pcbdattype in NEWDATA.H is the
IN-MEMORY structure the reader fills, not the file.  A synthetic
PCBOARD.DAT made by writing that struct to disk - which is exactly what
the first harness attempt did - is a file PCBoard cannot read.  That is
why Clark's PACKFIDO.EXE created ".@@@" and ".ADD" with an empty
basename and then hung: it read a text file as a struct, got an empty
CnfFile, and built the CNAMES names from nothing.

THREE SOURCES, THREE ANSWERS, AND THE FILE WINS
-----------------------------------------------
AREAS.DAT record size:

  FIDO.DOC - Clark's own documentation          81 bytes
  PACKFIDO.EXE disassembly - reads 0xF3        243 bytes
  Clark's actual AREAS.DAT, measured            71 bytes

  48,566 - 2 = 48,564 ; 48,564 / 71 = 684.0000 exactly
  684 records of 71 bytes after a 2-byte version header

and every field lands where it should:

  +2    conf=1  tag=NETMAIL           aka=0 org=0 hi=0 jd=0 priv=0 att=0
  +73   conf=3  tag=!CHINESE          aka=0 org=0 hi=0 jd=0 priv=0 att=0
  +144  conf=5  tag=4DOS              aka=0 org=0 hi=0 jd=0 priv=0 att=0

FIDO.DOC lays the record out as file offsets 2..82, which is 81 bytes.
The file is 71.  The difference is exactly the trailing Reserved[10]
the document lists - it is not in the data.  THE DOCUMENTATION IS WRONG
BY TEN BYTES about this very record.  Having the docs does not retire
the rule; it adds a third thing to check against the file.

PCBoard 15.22.  PACKFIDO.EXE carries internal date 11-10-94 and reads

config modules".

fixture.  THEY CANNOT BE RUN AGAINST EACH OTHER.  The acceptance diff
for PACKFIDO.C needs a version 1 or 2 AREAS.DAT, or a PACKFIDO built
for version 3.

  1. open("COM2", O_RDWR) - OS/2 exposes the port as a file, and a
     DOS box gets the same open/read/write/close handles a native
     OS/2 program gets.
  2. Control - speed, DTR, carrier - is INT 21h AX=440Ch, category
     CH=1 (ASYNCH), function in CL, ES:DI = command packet,
     DS:DX = data packet.

     DevIOCtl(Port,0x41,NULL,&BitRate)   set bit rate
     DevIOCtl(Port,0x46,&RetVal,&Mask)   DTR / modem control

  Tips it gives: writes never block, reads DO block unless the read
  timeout (function 53h) is set low, and ioctl is expensive - poll
  carrier on an interval, never in a tight loop.

THIS IS THE DOCUMENTATION FOR CODE WE ALREADY HAVE
--------------------------------------------------
The technique the document describes is implemented in the tree:

  pcb153\SOURCE\MODEM\DEVIOCTL.C     6,510 B  the INT 21h AX=440Ch wrapper
  pcb153\SOURCE\MODEM\DEVIOCTL.H              the prototype
  pcb153\SOURCE\MODEM\MODEMOS2.C              the caller

and MODEMOS2.C:442 is the document's own DTR example, verbatim:

  DevIOCtl(OSPort,0x01,0x46,&RetVal,sizeof(RetVal),&Mask,sizeof(Mask));

with the 4-argument DOS form on the next line under #else.  Same file
lives at pcb154\MAIN\SOURCE\MODEM\ and pcb153\upd154\SOURCE\MODEM\.

So OS2PORTS.DOC closes a loop rather than opening one: it is Clark's
public write-up of the private DEVIOCTL.C we have been compiling.  It
belongs beside the COMM-DRV / FOSSIL work, not beside PACKFIDO - and
it confirms the file formats need no OS/2 variant.

HOW IT BECAME POSSIBLE
----------------------
The blocker was: Clark's binary reads version 2 and the only Fido data
we hold is version 3.  The way past it was not to find a version 2 file
- it was to WRITE one.  The version 2 layout is fully specified by
Clark's own converter, MISC\FIDOUTIL\SOURCE\CONVERT.CPP, whose Areas()
reads a version 2 PCBFIDO.CFG field by field:

  fread(&numareas,sizeof(numareas),1,oldfile);
  for(i=0;i<numareas;i++) fread(&area,sizeof(area),1,oldfile);

with area an AREA_STRUCT - and convert() calls do_pack(), packfido's one
exported symbol, immediately before it, commented out.  The whole
program, in someone else's source, sitting in this repo the entire time.

The commented-out filter beside it is the same filter the binary
implements in machine code:

  if(confrec.Name[0]==' ' || confrec.Name[0]=='\0' ||
     confrec.ConfType != 5)   // pack out this conference

CONFIRMED BY EXPERIMENT, NOT BY READING
---------------------------------------
The fixture holds twelve conferences three and four times in SHUFFLED
order.  Clark's binary dropped exactly the later duplicates and kept the
first of each.  That is the first-one-wins behaviour that had only ever
been read out of the bit-CLEAR at 0x2F75.  It is now a measurement.

The fixture also covers conference 0, conference exactly == NumConf
(kept), one past it (dropped), 65535 (dropped), a conference with no
ConfType (dropped) and a Fido conference with no message base (dropped).
Its trailer is 1,031 bytes - deliberately not a multiple of 1,024, so
the short final chunk of the copy loop is exercised too.

TWO GENERATIONS, ONE PROGRAM
----------------------------
The 2-byte file version at offset 0 picks the layout.  Nothing is
guessed from the filename.

  version 2  PCBFIDO.CFG  15.21       version, COUNT, n x AREA_STRUCT
                                      (243), then a trailer copied in
                                      1K chunks and never parsed
  version 3  AREAS.DAT    15.22-15.4  version, then NAREA_STRUCT
                                      records to EOF.  No count, no
                                      trailer.

THE RECORD SIZE IS PROBED, NOT ASSUMED
--------------------------------------
  STRUCTS.H, sizeof(NAREA_STRUCT)        81
  FIDO.DOC, offsets 2..82                81
  Clark's own AREAS.DAT, measured        71

probe_v3() tries 81 first - what the header and the document both say -
then 71, and takes the first size that divides the file evenly AND
scans clean.  It prints which one it used.

This is also why the pack loop never declares a record variable.  In
BOTH generations the conference number is the first word and the name is
the 60 bytes after it, so the loop reads recsize RAW BYTES and touches
only those two fields.  Every byte it does not understand - including a
reserved[10] that may or may not be there - is copied through untouched.
A struct would have destroyed exactly the bytes in dispute.

A CORRECTION: THE CONFERENCE SCAN READS TWO FILES
-------------------------------------------------
pcbconftype is 739 bytes and THERE IS NO 739-BYTE FILE ANYWHERE.  It is
a MERGE of two records from two files, built by opencnames() and
getconfrecord() in toolkit\pwa153\SOURCE\TOOLKIT\CNAMES.C:

  CNAMES.@@@   short RecSize header, then oldconftype records, 548
               seek ConfNum*548 + 2
  CNAMES.ADD   NO header at all, addconftype records, 256
               seek ConfNum*256

Both indexed by the conference number DIRECTLY - conference 0, the Main
Board, is record 0.  CNAMES.DOC says (ConfNum-1); the code says ConfNum,
and the code is what wrote the files.

ConfType lives in CNAMES.ADD, not CNAMES.@@@.  CNAMES.ADD is OPTIONAL -
opencnames() only looks for it when PCBOARD.DAT says 15.0 and treats a
missing one as all zeroes.  A board without it has no Fido conferences
at all, which is correct: ConfType did not exist before it.

The previous PACKFIDO.C read one flat 739-byte-record file.  It read a
file that has never existed.  Corrected.

The in-memory offsets the disassembly gave were recomputed field by
field from NEWDATA.H and agree TO THE BYTE:
  Name +0x000   MsgFile +0x04A   ConfType +0x2D2   sizeof 739 = 0x2E3
which is why the binary's stack buffer is 0x2E4.

THE PORTABILITY WORK IS ONE TYPEDEF, AND IT MATTERED

"unsigned int" is 2 bytes under Borland C 3.1, Turbo C, MSC and 16-bit
wcc - and 4 BYTES UNDER wcc386 and every 32-bit target.

The conference number is the first two bytes of an AREAS.DAT record.

the next two bytes of every record - silently, no diagnostic, no crash,
just wrong answers about which areas to keep and a rewritten file.

short), and main() REFUSES TO RUN if pcbword is not 2 bytes.  That guard
is the second of the two W201 warnings on every target.

fallback for hosts without one, and the pack(1)/pack() pair kept because
Borland 3.1 has no pack(push)/pack(pop) while OpenWatcom has both.

never read through a struct - NAREA_STRUCT exists so the compiler can
confirm it packs to 81, and the pack loop then works on raw bytes at
fixed offsets.  A build that forgot -zp1 is still correct rather than
silently wrong, and the makefile says so.

v0.3.3+ (30): the version 2 PCBFIDO.CFG layout, read out of Clark's binary
==========================================================================
Date: 2026-09-23

No version 2 PCBFIDO.CFG survives anywhere.  The layout was READ OUT OF
THE CODE of the shipped FIDOUTIL.EXE - pcb1541\install\dist\target,
214,586 bytes, sha256 7b5eed4041ba..., whose strings date it to 15.22 /
1995 ("Convert 15.21 data to 15.22 format?", "Copyright Clark Development
1995").  The source in this tree is the later one - 15.23 / 1996.

METHOD
------
convert() walks the v2 file SEQUENTIALLY, one fread per record, writing
each block to its own .DAT.  Every fread goes through one routine at
0x483D and Borland loads the size as mov ax,imm16 a few instructions
before the call.  Disassembling from 0xC000 and pairing each call with its
preceding immediate recovers the whole read order - 49 fread sites, the
first eleven being convert().

THE LAYOUT
----------
  code      size  struct         what               became
  --------  ----  -------------  -----------------  --------------------
  0xC71C     243  AREA_STRUCT    area records       AREAS.DAT (81 / 71 on disk)
  0xC900    1168  ARCHIVERS      archiver table     stays in PCBFIDO.CFG
  0xC915     594  DIRECTORIES    9 x MAXFLEN 66     stays in PCBFIDO.CFG
  0xC92A     230  EMSI_DATA      EMSI {IDENT}       stays in PCBFIDO.CFG
  0xCAF0      47  NODE_T         per-node archiver  NODEARC.DAT (NNODE_T 22)
  0xCC30      43  THIS_ADDRESS   EMSI address list  AKAS.DAT (NADDRESS 92)
  0xCD7D      70  TRANSLATE      phone translation  PHONEX.DAT
  0xCE81     101  NODELIST       nodelist compile   NODELIST.DAT
  0xCF86      80  FREQ_PATH      freq paths         FREQPATH.DAT (NFREQ_PATH 86)
  0xD06B      15  FREQ_INFO      freq restrictions  stays in PCBFIDO.CFG
  0xD169      80  FREQ_MAGIC     magic filenames    MAGICNAM.DAT (NFREQ_MAGIC 106)

IN THE V2 FILE, ARCHIVERS COMES BEFORE DIRECTORIES.  In the v3 file
TMPtoCFG() writes it LAST.  The block order is NOT preserved by the
conversion - which is why reading a v3 file in the v2 order, or in the
PCBFIDO.TMP order, puts every field wrong.

The four blocks that STAY in PCBFIDO.CFG are exactly the four Clark's own
docs\PCBXDOT\DOCDEV\FIDO.TXT documents.  Everything else became a .DAT.

EMSI HERE IS THE FTSC PACKET, NOT A CLARK INVENTION
---------------------------------------------------
docs\fido\FSC-0056.txt defines EMSI_DAT and its addon fields.  The {IDENT}
addon is

  {IDENT}{[system_name][location][sysop][phone][baud][flags]}

which is EMSI_DATA field for field - BBS_Name[60] City[30] Sysop[30]
Phone[50] Baud[10] Flags[50].  Clark's larger Emsi struct is the WHOLE
EMSI_DAT packet: addr[2000] pw[25] line[20] codes[50] prodcode[50]
prodname[50] prodver[10] prodserial[50] then the six IDENT fields -
matching the spec's system address list, password, link codes,
compatibility codes, mailer product code, name, version, serial.

So: Emsi is the wire packet, EMSI_DATA is the part a sysop configures, and
THIS_ADDRESS is the system address list that later moved to AKAS.DAT.

WHAT IT SETTLES ABOUT FILE B, AND WHAT IT DOES NOT
--------------------------------------------------
B is 2009 bytes and 2+594+230+15+1168 = 2009, so B fits the v3 shape
ARITHMETICALLY, exactly as A does.  What does not fit is the CONTENT:
B's directory slot 6 holds "Stan's Test 2", a BBS name, where A holds a
path.

SUM to 132 - FREQ_LIMIT x 4, NNODE_T x 6, MAXFLEN x 2 - all fail that
boundary test.

The binary answers what it can: the complete v2 layout, which block became

v0.3.3+ (34): CORRECTION - 0x483D is memset, not fread. (30) and (32) wrong.
=============================================================================
Date: 2026-09-23

The v2 layout table in section (30) and PCBFIDO-V2.md was built by pairing
record sizes with calls to 0x483D on the assumption that it was fread.

IT IS memset.  Argument pattern (size, 0, ptr), 136 call sites.
  fread  = 0x3FD6   28 sites
  fwrite = 0x4246   27 sites
  memset = 0x483D  136 sites

Borland emits memset(&x,0,sizeof(x)) right before reading into x, so most
sizes came out right anyway - BUT NOT THE ONE THAT MATTERED.  The directory
entry reported 594, which is the memset of the NINE-entry destination.  The
actual fread is at 0xC9A0 and reads 396.

THE CLAIM IN (30)/(32) WAS WRONG
--------------------------------
"that binary never read a file shaped like B - its DIRECTORIES read is 594,
not 396" - WRONG.  The shipped 1995 FIDOUTIL.EXE reads
sizeof(OLDDIRECTORIES) = 396, exactly as the 1996 source does.
OLDDIRECTORIES is NOT a later addition.

ArchiverInfo() AS THE BINARY ACTUALLY HAS IT
--------------------------------------------
  0xC900  memset(rec,  0, 1168)
  0xC915  memset(dirs, 0,  594)    <- destination is the NINE-entry struct
  0xC92A  memset(emsi, 0,  230)
  0xC976  fread (rec,   1168)       ARCHIVERS
  0xC9A0  fread (dirs,   396)       OLDDIRECTORIES - SIX directories
  0xC9BC  fwrite(dirs,   594)       DIRECTORIES - NINE, tail zeroed
  0xC9E6  fread (emsi,   230)       EMSI_DATA
  0xCA02  fwrite(emsi,   230)
  0xCA2A  fwrite(rec,   1168)

Line for line the 1996 source.

WHAT IT DOES TO FILE B
----------------------
0xC915 zeroes dirs BEFORE the 396-byte read, so the 198-byte tail the
converter writes is ZEROS.  B has "Stan's Test 2" at +398, inside that

v0.3.3+ (39): probeLayout rewritten — size arithmetic replaces content heuristic
================================================================================
Date: 2026-09-23

THE HEURISTIC WAS WRONG IN PRINCIPLE
------------------------------------
Section (24) added probeLayout() with a content heuristic: walk nine
66-byte directory slots, call slotIsPath() on each, and if slot 6 fails
then the file must be the old six-directory generation.  "Stan's Test 2"
in the demo file's slot 6 position was enough to reject it as a path.

That works until someone names a directory "C:\STAN" or until an EMSI
field happens to look like a path.  The heuristic tests CONTENT, not
STRUCTURE.  The file's own arithmetic settles the question without
looking at content at all.

THE FIX: SUBTRACT THE KNOWN BLOCKS
-----------------------------------
Every PCBFIDO.CFG has exactly four fixed-size blocks:

  2 bytes         version word
  sizeof(EMSI_DATA)   230 bytes
  sizeof(FREQ_INFO)    15 bytes
  sizeof(ARCHIVERS)  1168 bytes
  ─────────────────────────────
  OVERHEAD           1415 bytes

Everything else is directories, at 66 bytes each.  So:

  dirspace = filesize - OVERHEAD
  if dirspace mod 66 != 0  ->  refuse (corrupt or unknown generation)
  ndirs = dirspace / 66

Nine directories means the new layout.  Fewer means old.  No content
inspection, no slotIsPath(), no guessing.

VERIFIED AGAINST BOTH REAL FILES
  A (2009 B)  ->  (2009 - 1415) = 594 ;  594 / 66 = 9.0  ->  NEW
  B (1811 B)  ->  (1811 - 1415) = 396 ;  396 / 66 = 6.0  ->  OLD

Both match the previous heuristic's answer.  The arithmetic also handles
any count cleanly — seven directories, twelve, whatever a future version
might use — without needing a new heuristic written for it.

slotIsPath() REMOVED.  It was a static function used only by the old
probeLayout() and has no callers.

DEFINES REPLACED
  OLD:
    #define PCBFIDO_NEWDIRS      9
    #define PCBFIDO_OLDDIRS      6
    #define PCBFIDO_OLDDIRBLOCK  ((unsigned long)PCBFIDO_OLDDIRS * (unsigned long)MAXFLEN)
  NEW:
    #define PCBFIDO_OVERHEAD     (2L + (long)sizeof(EMSI_DATA) + (long)sizeof(FREQ_INFO) \
                                  + (long)sizeof(ARCHIVERS))
    #define PCBFIDO_NEWDIRS      9

PCBFIDO_OLDDIRS and PCBFIDO_OLDDIRBLOCK were only used by the old
heuristic.  PCBFIDO_NEWDIRS stays — the threshold for "new layout".

putDirs/putEMSI/putFREQInfo comment block updated to say "directory count
is below nine" instead of "six directory generation".

pcb153\SOURCE\MISC\FIDOUTIL\PCBFIDO-V2.md closing paragraph updated to
reflect the size-arithmetic probe.
