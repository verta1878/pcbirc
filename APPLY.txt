v0.3.2: ROOT names the branch; paths match our layout; three recoveries
=======================================================================
Date: 2026-09-17

Thirteen makefiles in pcb153 now say which branch they belong to and
point at directories that exist in this repo.  Plus three things that
were recorded as missing and were not.

ROOT NAMES THE BRANCH
---------------------
Clark wrote `ROOT = \PROJ` for a company with one product.  This tree is
one of four.  All eleven makefiles that declared a root now say:

    !ifndef ROOT
    ROOT     = \PWA153
    !endif

The guard is not decoration.  Borland MAKE 3.6 lets a MAKEFILE
definition beat a `-D` command-line macro -- the opposite of GNU make --
so `MAKE -DROOT=\DELTA154` silently does nothing without it.  Tested
both ways, before and after.

Left alone on purpose: 153/PCBOARD.MAK had `ROOT = ..`, already
branch-neutral by being relative and arguably the better pattern.
PPLC.MAK and USERNET2.MAK declare no ROOT at all.

PATHS REPOINTED TO OUR LAYOUT
-----------------------------
  $(LIBROOT)\BCDOS\$(BCCOMPILER)  ->  $(LIBROOT)\$(BCCOMPILER)\lib
      12 references.  BCCOMPILER is already bc31, so this resolves to
      toolkit/pwa153/bc31/lib/ -- where the category libraries moved in
      v0.3.1.

  $(ROOT)\PCB\SOURCE              ->  $(ROOT)\SOURCE
  $(ROOT)\MAIN\SOURCE             ->  $(ROOT)\SOURCE
  $(ROOT)\PCBSM\SOURCE            ->  $(ROOT)\SOURCE\UTIL\PCBSM\SOURCE
      35 paths across 10 makefiles.  ROOT already names a PCBoard
      branch; \PCB said it twice and named nothing.  \PCBSRC, which
      appeared in two makefiles, was not Clark's and named nothing
      either.

Verified by rebuild, not by inspection.  PCBOARD.EXE after the repoint:
955,904 B, sha256 b55719144e359fbc5d6cdf0f4fce401c8b7366476df8a22d179bc1469f6f7a45
-- byte-identical to the pre-change binary.  The repoint changes where
the linker looks, not what it emits.

THREE RECOVERIES
----------------
VMData -- CLARK-DRIVE-LAYOUT.md called it "missing everywhere" and named
it the gate on most of the 15.3 utility set.  The source was in
pcb154/LIB/ and it is not Clark's: VMAVL.C and vmavl.h are clean-room
GPLv3 by sysop/0, VMFUNCS.C is hexadecimal v0.036.  The crew had written
a replacement and nothing said so.  Copied to
toolkit/pwa153/{SOURCE,H} -- zero Watcom markers, so Borland takes it
unmodified.  VMDATA.LIB still needs building; 7 utilities stay blocked
until it is, but the blocker is a build step now, not a missing file.

md5\os2\md5.obj -- referenced by PCBOARD2.MAK against an object that
existed nowhere.  It was in devtools/Md5.zip.  Recovered to
pcb153/SOURCE/MISC/MD5/ with MD5.ASM, MD5.TXT and the RFCs.  OS2/ is not
a guess: MD5.ASM has zero INT 21h and zero Dos* calls but exports
DoThunk32to16 and FlatToSel -- 32<->16-bit thunking, which DOS has no
use for.  PCBOARD2.MAK repointed.  ARSENAL.LIB from the same zip was NOT
copied; it is a text advertisement with a .LIB extension.

packfido.c -- cannot be fixed.  FIDOUTIL.MAK builds packfido.obj and the
string `packfido` appears in exactly one place across the whole archive
and repo: that makefile.  There is nothing to repoint to.  Recorded as a
real gap.

normalize-case.sh
-----------------
  MAIN/build/scripts/normalize-case.sh   (new)

Supersedes pcb154/normalize_case.sh, which covered three directories in
one branch and no toolkit tree at all -- so toolkit/<branch>/H had never
been normalised by anything, while the OpenWatcom Linux build is how
delta154 and irc1541 are meant to be built.  The new one covers all four
branches plus the program trees, has a --check dry run, and exits 2 on a
case clash where two files differ only in filename case AND content.

THE COPIES IT MAKES ARE BUILD OUTPUT.  Run it against a staged build
root, not the repo you commit from.

.gitignore
----------
  + !pcb153/SOURCE/MISC/MD5/OS2/*.OBJ    (source material, not output)

and the v0.3.1 LAST WORD block restored -- it was lost twice this
session, both times by committing .gitignore from a staged copy that
predated an edit to it.  The second loss silently reverted a fix made an
hour earlier and put the 12 sample doors back out of git's sight: the
same mechanism that lost Clark's binaries in the first place.
Rebuilt from the live file; 13 paths simulated against the rules, 0
hidden.

TWO DIVERGENCES THIS UNCOVERED
------------------------------
PCBSM.MAK and MKPCBTXT.MAK had already been rewritten, unrecorded --
`ROOT = \PCBSRC`, 221 and 48 lines differing from the PCBSRCV/000
originals, the \LIBS\VMDATA include dropped, and MKPCBTXT changed from
small to LARGE memory model.  Only the root name was normalised here;
the rest was left as found.  Reverting work whose reason is unknown is
worse than recording it.

OUT/pwa153/PCBOARDM.EXE and PCBOARD.EXE were built from the ARCHIVE
tree (PCBSRCV/014), not from pcb153/SOURCE.  They link and they run, but
the archive carries a 15.4 leak (CALLWAIT.C:1460 SPACERIGHTAT vs the
repo's SPACERIGHT) and lacks MD5IMPL.CPP, which the repo's PCBOARD.MAK
builds.  They are real binaries but they are not this repo's output.
Flagged, not quietly replaced.

VIRTUAL1.C -- v0.3.1's "ORIGINAL" WAS NOT ORIGINAL
--------------------------------------------------
v0.3.1 restored toolkit/pwa153/SOURCE/MISC/VIRTUAL1.C and called it the
only unmodified copy.  It carried one port fix:

    -#include <stat.h>
    +#include <sys/stat.h>

All five copies in the repo were modified; Clark's original survives only
in the archive.  Replaced with PCBSRCV/000/LIB/SOURCE/MISC/VIRTUAL1.C,
CRLF -> LF to match the tree (6,432 -> 6,207 B), content otherwise
byte-identical.

VIRTUAL.C is NOT touched.  Note what it is, though: the repo's copy
(14,610 B) is a crew-MERGED file carrying both implementations behind
#define VIRTUAL_HUGE, with the headers merged the same way.  Its
huge-pointer half is byte-identical to Clark's VIRTUAL.C.  That merge
sits in what is supposed to be the frozen preservation base.  Recorded,
not reverted -- and the merged header still serves the restored
VIRTUAL1.C correctly, since undefined VIRTUAL_HUGE yields VIRTUAL1's ABI.

VIRTUAL.C and VIRTUAL1.C are NOT duplicates of each other: same
seven-function API, incompatible signatures (huge/long/cached vs
near/unsigned/uncached), identical symbol names, so a program links one
or the other.

FIDOUTIL.EXE WAS NEVER ACTUALLY BLOCKED
---------------------------------------
Its missing 11th module, packfido.obj, supplies one symbol -- do_pack().
Every occurrence of do_pack in the entire archive:

    MISC/FIDOUTIL/SOURCE/CONVERT.CPP:53    void do_pack(void);
    MISC/FIDOUTIL/SOURCE/CONVERT.CPP:124     //do_pack();

A declaration and a commented-out call.  Checked against all eleven
inputs; CONVERT.CPP is the only file that mentions it.  The object
contributed nothing to the linked image.  Dropped from EXE_DEPENDENCIES
and the linker response list; build rule commented, not deleted.
FIDOUTIL builds today with its ten real modules.

THE 37-EXE TARGET, AUDITED
--------------------------
todo/PCBIC-PWA-BUILD-DRAFT.md now carries the breakdown.  Four numbers
were being conflated:

    37  shipped by the 15.3 installer
    24  have a makefile somewhere
    11  present in the packaged build root
     2  actually built

Tier 2 is the cheap win: PCBOARD, PCBOARDM, PCBOARD2, PPLC100, PPLC330
are blocked only because BUILDROOT/PCB153/ has no 153\ directory --
COMPILE.BAT is there, the makefiles it invokes are not.  Fixing
DOSBOXX.ZIP unblocks five binaries including the main one.

Tier 3 is 13 utilities whose source and makefiles sit in PCBSRCV/000/
and were never imported.  A copy, not a recovery.

Tier 4 is 13 with no source AND no binary.  Every Clark binary the repo
holds was inventoried: 18 of them, and not one is a Tier 4 target.
Nothing in that tier can be decompiled until a 15.3 distribution turns
up.  One of the 13, DOORWAY.EXE, is Marshall Dudley's third-party door
driver and was never Clark's to begin with.

Also flagged: the OUT/data/ layout the draft describes across ~15
sections is a plan, not a state.  OUT/data/ contains ic12/ and nothing
else.

LESSON
------
Everything wrong in this release was a path or a claim nobody had
checked against the thing it described.  \PROJ named nothing, \PCBSRC
came from nowhere, BCDOS\BC31 pointed where the libraries no longer are,
VMData was "missing" while sitting in pcb154, md5.obj was referenced for
thirty years against an empty directory, FIDOUTIL was blocked on a module
nothing calls, a restored "original" carried a port fix, and a .gitignore
got broken by the person documenting how .gitignore breaks things.

After committing any file that governs what gets committed: re-read it
from disk and verify the RULES, not the bytes.


v0.3.1: the pwa153 door SDK, built and verified by linking
===========================================================
Date: 2026-09-17

The first SDK library this project has produced, plus the sample doors
that prove it works, plus corrections to what earlier sessions recorded
as finished.

PCBKBC — THE DOOR SDK
---------------------
  toolkit/pwa153/bc31/lib/   PCBKBC{S,C,M,L}.LIB
                             152 modules, 4 memory models
                             + .LST listings, CHECKSUMS.sha256/.md5

  OUT/pwa153/bins/medium/    6 sample doors, linked against PCBKBCM.LIB
  OUT/pwa153/bins/large/     6 sample doors, linked against PCBKBCL.LIB
                             HELLO, CALLBACK, COPYTEXT, COPYBIN1,
                             COPYBIN2, UPGRADE  (Clark's own samples)

  MAIN/build/scripts/        BLDKBC.BAT (replaced), PCBKBC.CFG,
                             KBC{S,C,M,L}.RSP

150 of 150 functions in Clark's shipped TOOLKIT/OTHER/QUICKREF are
present -- 139 by name, 11 as the ASYNC_* entry points the headers map
them to.  Nothing unresolved.

THE CONFIG: THREE SWITCHES OUT, PLUS -DLIB
------------------------------------------
Clark shipped no door-SDK config.  LIB/CFG/BC31/PCBOARD.CFG is the
PCBOARD.EXE config.  The SDK config is that, plus -DLIB, minus:

  -Y          overlay generation.  Borland only allows overlays in
              medium/large/huge.  This -- not far pointers, not
              _FARDATA_ -- was the small/compact blocker that
              SDK-BUILD-STATUS.md had called "more work than a re-run".
              6/130 objects became 130/130.

  -DPCBCOMM   guards PCBoard-internal branches reading Status.TerseMode,
              which does not exist in the door-visible statustype that
              -DLIB selects.  All four -DPCBOARD/-DPCBCOMM combinations
              were compiled to find which one mattered.

  /DCPU386    only BUG.H reads it, to reach a long BC386BUG global in
              MAIN/SOURCE/MAIN/PCBOARD.C -- a file no door can link.
              -3 stays; the code is still 386.

KEEP -D_FARDATA_=_FAR_ and -P.  The previous BLDKBC.BAT omitted both,
along with -V -Vmp -Vmd.  A library built that way hands doors a struct
layout that disagrees with PCBOARD.EXE at runtime, silently.

MANIFEST: pcbkit_l.lib IS NOT THE SDK
-------------------------------------
The inherited 119/130-module manifest came from pcbkit_l.lib.  That is
the PPLC/utility link target (PCBSETUP links it too), built WITHOUT
-DLIB, and docs/pcboard-internals/PCBKIT-LIB.md already recorded it as
stale.  Cost of using it:

  3 wrong-tree picks   CNAMES, HELP -> SOURCE/TOOLKIT/
                       ANSI -> pcb153/SOURCE/ASM/ANSI.ASM, tasm /m3.
                       Not either ANSI.C: the DISPLAY one looks right
                       but will not compile under -DLIB, and the linker
                       wants those symbols UPPERCASE.
  22 absent modules    each traced from a linker "Undefined symbol"
  2 modules removed    SCRNIO/GETKEY.C and DOS/SHOWERR.C are
                       PCBSETUP-side.  The door-side replacements
                       (SMALLERR.C, NOINPUT.C) already ship.

TWO LIMITS, NEITHER A DEFECT
----------------------------
  Small and compact fail every sample with "Segment _TEXT exceeds 64K".
  One code segment; initdoor's closure is bigger on its own.  Those
  libraries are for doors using a small slice of the toolkit -- which is
  why Clark shipped four models.  No S/C binaries in bins/.

  SAMPLES/INPUTREQ.C fails with "Undefined symbol _MAIN".  It is a
  replacement-module example, meant to be compiled into a door rather
  than linked standalone.  TLINK emits an invalid .EXE, so it is not
  shipped.

CATEGORY LIBRARIES MOVED
------------------------
  OUT/pwa153/lib/*.LIB  ->  toolkit/pwa153/bc31/lib/

Same source tree, same compiler, and Clark kept his in LIB/BCDOS/BC31/ --
inside the library tree, not an output directory.  They are NOT built by
BLDKBC.BAT (which builds only the SDK); they come from Clark's
per-directory MAKEFILEs via COMPILE.BAT -> PCBOARD.MAK.

  The old OUT/pwa153/lib/ copies must be deleted by hand -- this
  session could not delete on the local machine.  Contents verified
  byte-identical (SHA256) before the copy.

LESSON
------
A count is not a verification.  "130/130 modules" and "DONE, all 4
models" were both recorded in good faith and both wrong, because nothing
had tried to USE the output.  Linking one sample door found a
misidentified source tree, 22 missing modules, two modules that did not
belong, and a config that would have produced silently incompatible
structs.  Build the smallest real consumer of an artifact before
believing the artifact is finished.
