1.  SUMMARY OF 15.4 ADDITIONS
═══════════════════════════════════════════════════════════════════════════════

Bug fixes (all documented in Clark's HISTORY file):

  UUIN.EXE  04/22/97
    "Now supports 'multipart/alternative' MIME encoding."
    → HTML-plus-text mail no longer dumps HTML tags into your mail
      conference; the plaintext part is chosen.

  PCBSM.EXE  04/18/97
    "Fixed the default 'M' for Gender to be empty until the user
     specifies either 'M' or 'F'."
    → New users don't get assigned an arbitrary gender.

  PCBSM.EXE  04/22/97
    "If a PCBoard PSA wasn't installed, you were still allowed to edit
     the information for the PSA.  Fixed."
    → PCBSM refuses to edit PSA fields when the underlying PSA is not
      installed, instead of silently discarding your edits.

New features:

  Personal PSA
    Four new per-user fields: Gender, Birthdate, Email address, Web
    (home page) URL.  Stored as a new "PCBPERSONAL" PSA in USERS.INF.

  URead.ShortDesc field
    A per-user "short description mode" flag added inline in the URead
    struct, consuming one byte of the previously-Reserved 390-397 window.
    Sysops can toggle it during registration via TXT_USESHORTDESC.

  PPL 3.40 additions (5 new functions + 3 new statements)
    Functions: U_PERSONAL(idx), SHORTDESC(x), GETBANKVAL(idx), GETMSGHDR(m,f),
    SETMSGHDR(m,f,v).
    Statements: MOVEMSG, SETBANKVAL, SHORTDESC.

  MD5LOGIN environment variable  (v0.025 activation)
    When a caller connects and their terminal sends a 32-hex-digit
    MD5 challenge, PCBoard stores the digest and exposes it to any
    external door as the env var MD5LOGIN=<digest>.  Doors that
    support MD5 auth can verify the caller was actually logged in
    through PCBoard rather than launched standalone.  Optional —
    terminals that don't send an MD5 string log on normally with
    no MD5 data set.

  PCBTEXT prompts 747-750
    Prompts for Gender / Email / WEB / Birthdate registration.

2.  ORDER OF UPGRADE OPERATIONS  —  READ THIS FIRST
═══════════════════════════════════════════════════════════════════════════════

Do these in order.  Skipping any step breaks the following steps.

  Step 1.  BACK UP EVERYTHING.  Full copy of your PCB directory including
           USERS, USERS.INF, PCBTEXT.CDC, PCBOARD.DAT.  If any step goes
           wrong the fastest recovery is restoring from this backup.

  Step 2.  Take your BBS offline.  DO NOT let users register during the
           upgrade — new records written before Step 5 will be missing
           the Personal PSA and will need re-registration.

  Step 3.  Rebuild PCBOARDM.EXE, PPLC.EXE, MKPCBTXT.EXE, and PCBSM.EXE
           from the patched source (see section 3.1).

  Step 4.  Run MKPCBTXT PCBTEXT.CDC to upgrade the prompt file
           (section 3.2).  ONLY do this before running the new PCBOARDM.EXE
           for the first time — the new prompts are used by section 5.

  Step 5.  Run PCBSM, menu 7 → "Add PCBoard Supported Allocations" →
           menu 8 → "Personal Info Support" (section 3.3).  This adds
           the PCBPERSONAL app-header entry to USERS.INF and pads every
           existing user's record with 127 bytes of zero-initialized
           personal data.

  Step 6.  Verify with a test user (section 3.4).

  Step 7.  Bring the BBS back online.

3.  DETAILED MIGRATION STEPS
═══════════════════════════════════════════════════════════════════════════════

3.1  Rebuild the binaries
─────────────────────────

The build process is documented in the source tree's COMPILE.BAT files.
Prerequisites: Borland C++ 3.1 large model, DOSBox if you're not on real DOS.

  a) PCBOARDM.EXE  (main BBS binary, 32-bit protected mode)
       cd \pcbsrc\main
       call pcbsrc.bat
       call compile.bat

  b) PPLC.EXE  (PPL compiler — needed for the 5 new tokens)
       cd \pcbsrc\main
       call pplc.bat

  c) PCBSM.EXE  (sysop menu — needed for PSA install)
       cd \pcbsrc\main\source\util\pcbsm
       call compile.bat

  d) MKPCBTXT.EXE  (PCBTEXT upgrader)
       cd \pcbsrc\main\source\util\pcbtext
       call compile.bat

Any errors here mean the source tree is inconsistent — check CHANGES.TXT
to confirm you have the v0.023 (or later) revision applied.

3.2  Upgrade PCBTEXT.CDC
────────────────────────

    MKPCBTXT PCBTEXT.CDC

If you run non-English PCBTEXT files, also run MKPCBTXT against each of them:

    MKPCBTXT PCBTEXT.FRA
    MKPCBTXT PCBTEXT.GER
    (etc.)

MKPCBTXT reads the version stamp from record 0 of the file, appends any
missing records (there will be exactly 4 new ones in 15.4 — TXT_ENTERGENDER
through TXT_ENTERBIRTHDATE — plus a version-stamp rewrite of record 0), and
writes back in place.  Old sysop customizations to records 1-746 are
preserved untouched.

Default text for the new records (record numbers per PCBTEXT.H):

    747  Enter your gender (M/F)
    748  Enter your E-mail address
    749  Enter your WEB address
    750  Enter your birthday (MM/DD/YY)

You can customize these to your board's tone — edit PCBTEXT.CDC with any
editor that respects the 80-byte-record on-disk layout (or use PCBSM's
"Change PCBTEXT File" menu).

TO DISABLE A PROMPT: blank out the record's text (leave just the color
byte plus spaces).  LOGIN.C skips any prompt whose PCBTEXT record is
empty.  This is how a sysop who doesn't want to ask for Web addresses
would suppress prompt 749 without needing a source change.

3.3  Install the Personal PSA in PCBSM
──────────────────────────────────────

Run PCBSM.  From the main menu:

    7 (User Info File Maintenance)
      → 3 (Add PCBoard Supported Allocations)
        → 9 (Personal Info Support)     [new in v0.022]

Confirm with Y when prompted "Proceed with Add/Update of PSA".  PCBSM
will:

    - Add an app-header entry to USERS.INF header with:
        Name       = "PCBPERSONAL"
        Version    = 10
        SizeOfRec  = 127     (1 byte Gender + 6 Birthdate + 60 Email + 60 Web)
        SizeOfConfRec = 0    (no per-conference data)

    - Rebuild every USERS.INF record with 127 more bytes appended,
      zero-initialized.  Users created before this step will have
      Gender = 0 (NUL), which for the runtime means "unset" — same as
      the 15.4 fix intent.  They'll be prompted for their info the next
      time they answer a script that references U_PERSONAL(), or you
      can force it by adjusting your PCBoard registration flow.

    - Set PersonalSupport = TRUE in memory and PersonalOffset to the
      new PSA's byte offset.

You can verify installation via menu 7 → 2 (List Installed PSA/TPA Areas).
PCBPERSONAL should now appear.

3.4  Verify with a test user
────────────────────────────

  a) Log in as a NEW user.  You should see the 4 new prompts appear:
        Enter your gender (M/F)
        Enter your birthday (MM/DD/YY)
        Enter your E-mail address
        Enter your WEB address

  b) Log in as the new user again.  Run a PPL script (either write your
     own or use the built-in @X sequences) that queries U_PERSONAL(3):

        STRING email
        LET email = U_PERSONAL(3)
        PRINTLN "Your email on file: " + email

  c) Run PCBSM, edit that user's record, choose menu 2 (individual user
     edit).  You should now see additional fields for Gender / Email /
     Web / Birthdate.  Change one, save, log in as the user again,
     re-query U_PERSONAL to confirm the change persisted.

4.  NEW PPL FUNCTIONS AND HOW TO USE THEM
═══════════════════════════════════════════════════════════════════════════════

This section is based on Clark's WHATSNEW document (pcb154b/WHATSNEW, Apr
1997) cross-checked against the compiled PPLC.EXE 15.4b token table.  Where
the two disagreed, WHATSNEW wins — the compiled token table shows what the
parser accepts, WHATSNEW documents what sysops are told the tokens mean.

4.1  U_GENDER, U_BIRTHDATE, U_EMAIL, U_WEB, U_SHORTDESC — VARIABLES
────────────────────────────────────────────────────────────────────

Individual per-user variables added in 15.4.  All are STRING type except
U_SHORTDESC which is BOOLEAN.  Read/write directly like any other
PPL user variable — no accessor call needed:

    STRING gender
    LET gender = U_GENDER              ' read
    LET U_EMAIL = "user@example.com"   ' write

Registered by the compiler at MAIN/SOURCE/PPL/SCRCOMP.CPP:

    doVariable(vtBOOLEAN, "U_SHORTDESC", -1, pass);
    doVariable(vtSTRING,  "U_GENDER,U_BIRTHDATE,U_EMAIL,U_WEB", -1, pass);

At runtime these read/write directly into the Personal PSA.  Silent
no-op if PersonalSupport is FALSE.

4.2  U_PERSONAL(idx)   — indexed accessor (alternative form)
─────────────────────────────────────────────────────────────

The 15.4b binary also exposes U_PERSONAL(idx) as a function-style
accessor.  Semantically equivalent to the individual variables in
section 4.1; you can use either form depending on script clarity:

    idx = 1    Gender      — same as U_GENDER
    idx = 2    Birthdate   — same as U_BIRTHDATE
    idx = 3    Email       — same as U_EMAIL
    idx = 4    Web         — same as U_WEB

    STRING gender
    LET gender = U_PERSONAL(1)         ' equivalent to U_GENDER

Useful when the index is dynamic:

    INTEGER field
    FOR field = 1 TO 4
      PRINTLN U_PERSONAL(field)
    NEXT

4.3  SHORTDESC() function / SHORTDESC statement
───────────────────────────────────────────────

Read/write the current caller's short-description mode:

    LET flag = SHORTDESC(0)      ' read current mode (argument unused for now)
    SHORTDESC 1                  ' set short-descriptions mode
    SHORTDESC 0                  ' set long-descriptions mode

For reading the caller's own setting the U_SHORTDESC variable (section
4.1) is simpler and equivalent.

4.4  GETBANKBAL(field) / SETBANKBAL statement — Time Bank PSA
──────────────────────────────────────────────────────────────

** IMPORTANT CORRECTION vs. earlier revisions of this doc **

Per WHATSNEW, the banking PSA introduced in 15.4 is a TIME BANK, not
an account-balance PSA.  It has 12 fields (0-11) covering time (in
minutes) and byte-transfer (in KB) accumulation:

    Time Fields (minutes)
    ─────────────────────
     0 = Last Deposit Date
     1 = Last Withdrawal Date
     2 = Last Transaction Amount
     3 = Amount Saved (current time balance)
     4 = Max Withdrawal (daily limit)
     5 = Max Stored Amount (all-time cap)

    Byte Fields (KB)
    ────────────────
     6 = Last Deposit Date
     7 = Last Withdrawal Date
     8 = Last Transaction Amount
     9 = Amount Saved (current KB balance)
    10 = Max Withdrawal (daily limit)
    11 = Max Stored Amount (all-time cap)

Syntax:

    LET amt = GETBANKBAL(3)           ' current time balance
    SETBANKBAL 3, amt + 10            ' deposit 10 minutes

Requires the Time Bank PSA installed via PCBSM (menu 8, entry to be
added by future v0.026+ work — the current PCBSM install screen has
"Personal Info Support" from v0.022 but not "Time Bank Support").

Historical note: pre-WHATSNEW versions of this document called these
GETBANKVAL/SETBANKVAL and described 16 fields covering
StartingBalance/DebitCall/etc.  That was based on RE of the accounttype
struct in USERS.H — the accounttype struct exists but is the ACCOUNT
PSA (15.3 era), NOT the Time Bank PSA (15.4).  Two different PSAs.

The compiled tokens in PPLC 15.4b are GETBANKVAL/SETBANKVAL (V not B)
— so scripts must use those names to compile, even though WHATSNEW
documents them as GETBANKBAL/SETBANKBAL.  This is either a beta-cycle
rename that WHATSNEW documented ahead of the binary, or a Clark-side
typo.  The PPL parser is case-insensitive so either casing works.

4.5  GETMSGHDR(conf, message, field) — read msg header field
─────────────────────────────────────────────────────────────

Reads a single header field from a message in the given conference.
The field index matches SCANMSGHDR() from PPL 3.00.

Syntax:
    result = GETMSGHDR(conf, message, field)

    conf     INTEGER — conference number of the message base
    message  DOUBLE  — message number (msgnums are 32-bit)
    field    INTEGER — 0..15 header field (see SCANMSGHDR docs)

Common fields:
    HDR_TO       1
    HDR_FROM     2
    HDR_SUBJ     3
    HDR_PWD      4
    HDR_STATUS   6
    HDR_DATE     7
    HDR_TIME     8

Example — get who the last message is addressed to:

    STRING toName
    LET toName = GETMSGHDR(0, HIMSGNUM(), HDR_TO)
    PRINTLN "The last message is addressed to ", toName

4.6  SETMSGHDR(conf, message, field, value) — write msg header
───────────────────────────────────────────────────────────────

Writes one header field.  Sysop-level access required.

Syntax:
    SETMSGHDR(conf, message, field, value)

    conf     INTEGER — conference number
    message  DOUBLE  — message number
    field    INTEGER — 1..5 writable subset (per WHATSNEW):
                        1 = 'To' field
                        2 = 'From' field
                        3 = 'Subject' field
                        4 = 'Password' field
                        5 = 'Echo' Flag
    value    STRING  — new value

4.7  MOVEMSG conf message movetype — move/copy a message
─────────────────────────────────────────────────────────

Statement (not function).  Moves or copies a message to the end of the
message base.

Syntax:
    MOVEMSG conf, message, movetype

    conf      INTEGER — conference number
    message   DOUBLE  — message number
    movetype  BOOLEAN — TRUE = move (delete source), FALSE = copy

Example — move the lowest message to the end:

    INTEGER LowMessage
    LET LowMessage = LOMSGNUM()
    MOVEMSG 0, LowMessage, TRUE

Errors printed at runtime (verbatim from PCBOARDM.EXE 15.4b):
    "Conference does not exist (MOVEMSG)"
    "Message number does not exist (MOVEMSG)"
    "Unable to read message body (MOVEMSG)"
    "Unable to read message header (MOVEMSG)"

STATUS in the current port: MOVEMSG, GETMSGHDR, and SETMSGHDR are
FULLY LANDED as of v0.028.  The msg-base I/O helpers (GetMsgHdrSub,
SetMsgHdrSub, pplmovemsg) live in MAIN/SOURCE/PPL/EVALP.CPP alongside
the existing ScanMsgHdrSub and use the same cMSG / pcbmsghdr API.
Scripts calling these functions read/write real message headers and
move/copy messages between message-base positions as documented.

Sysop caveat: SETMSGHDR does NOT check sysop-level access at the
helper level; the caller (your PPL script) is expected to guard on
Status.ActStatus or U_SEC before invoking.  Casual users should not
be able to rewrite arbitrary message headers.

4.8  MD5LOGIN environment variable  (activated in v0.025)
──────────────────────────────────────────────────────────

Not a PPL feature — an environment variable set by PCBoard when
spawning external doors.  Documented here because sysops writing
doors will want to know it's available.

How it works
────────────

  1. Caller's terminal / gateway sends a bracketed 32-char hex string
     during modem sync:
         <XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX>
     Standard 32-hex-digit MD5 digest between < and >.

  2. PCBoard's INKEY.C detects the sequence, stores the digest in
     ReceivedMd5String[35], and displays "MD5 String Received!" on
     line 24.

  3. The full formatted string (including brackets) is logged to
     the callers log as `MD5LOGIN=<XXXXXX...>`.

  4. When PCBoard spawns any door, PCBOARD.EXE sets an env var:
         MD5LOGIN=<XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX>
     The door program reads getenv("MD5LOGIN") to consume it.

  5. If no MD5 was received during sync (silent connect, ANSI-only
     terminal, older gateway that doesn't do MD5), the env var is
     NOT set.  Doors that check should treat "getenv returned NULL"
     as "no MD5 auth available" rather than an error.

Requirements
────────────

  - Only works when PCBoard is compiled with -DCPU386 -DMULTIPORT
    (the 32-bit protected-mode build).  PCBoardM.EXE has it;
    PCBoard.EXE (16-bit real mode) does not.

  - The caller's terminal or comm gateway must send the MD5
    handshake.  Most terminals never will, unless the sysop has
    configured a gateway program in front of the modem that
    generates the MD5.

Why sysops should care
──────────────────────

  - Doors can now cryptographically verify they were spawned by
    PCBoard (not by a rogue user who somehow got shell access).

  - The MD5 digest is one-way, so even if the callers log leaks,
    the caller's password is not exposed.

  - Third-party utilities that pre-15.4 stored plaintext passwords
    in memory for shell-out purposes can now use the MD5 hash
    instead — the sysop never needs to make the plaintext available
    outside the USERS file.

Adding MD5 support to a door
────────────────────────────

    /* In your door's main() */
    char *md5 = getenv("MD5LOGIN");
    if (md5 == NULL || md5[0] == 0) {
        /* No MD5 available.  Fall back to trust-the-DOOR.SYS mode. */
    } else {
        /* Have <XXXX...XXXX>.  Compare against MD5(user_password + salt)
         * where the salt was pre-arranged with the gateway.  Or just
         * echo it back to prove door was spawned in this session.
         */
    }

6.  ON-DISK COMPATIBILITY NOTES
═══════════════════════════════════════════════════════════════════════════════

USERS file (fixed 400-byte record)
──────────────────────────────────
UNCHANGED.  Byte layout of URead is identical to 15.3.  The one 15.4
addition — ShortDesc — is packed into a byte of the existing
Reserved[8] scratch space (bytes 390-397 stay 8 bytes total).

Old 15.3 USERS files load cleanly.  Users created under 15.3 will read
ShortDesc as whatever was in Reserved[0] — which was zero for anyone
who registered on a stock system.  If you want to be careful, you can
run a one-shot PPL script that walks all users and sets ShortDesc to 0.

USERS.INF file
──────────────
GROWS by 127 bytes per user, once PCBPERSONAL is installed (see 3.3).

Header grows by sizeof(apptype) = ~15 bytes for the new PCBPERSONAL app
entry.

CRITICAL: after installing PCBPERSONAL, the file is NOT backward
compatible with 15.3.  Old PCBoard binaries reading this file will get
wrong record offsets for anything past USERS.INF header + old-record-size.

If you need to run both 15.3 and 15.4 simultaneously (e.g., a network
with mixed versions), DO NOT install PCBPERSONAL.  The runtime treats
PersonalSupport=FALSE as "the feature is disabled" — the code paths
that touch Personal.* are all guarded.  Everything except the four new
registration prompts continues to work.

PCBTEXT.CDC
───────────
GROWS by 4 records * 80 bytes = 320 bytes.  MKPCBTXT handles the
extension.  Old 15.3 binaries see 750 records but only reference the
first 746, so backward compat is fine as long as you don't shrink the
file.

PPE files (compiled PPL)
────────────────────────
BACKWARD COMPATIBLE.  The 5 new tokens have new negative opcodes
(-287..-291) that are ignored by 15.3 PPL runtimes if they never
appear.  A PPE that USES U_PERSONAL() etc. compiled by 15.4 PPLC will
NOT run on 15.3 PCBoard because 15.3's EVALP.CPP has no dispatch
handler for -287..-291.  Keep separate PPE builds if you support both.

7.  BACKING OUT TO 15.3
═══════════════════════════════════════════════════════════════════════════════

Order of operations to unwind:

  1. Take BBS offline.

  2. Run PCBSM:  menu 7 → 4 (Remove PSA From User Info File) →
     menu 8 → 9 (Personal Info Support).  This removes the PCBPERSONAL
     PSA and shrinks every user's INF record.  The Gender/Email/Web
     fields are LOST.

  3. Replace PCBOARDM.EXE, PPLC.EXE, PCBSM.EXE, MKPCBTXT.EXE with your
     15.3 backups.

  4. Replace PCBTEXT.CDC with your 15.3 backup (or truncate to 746
     records manually — records 747-750 are ignored by 15.3 anyway,
     so you can leave them, they just waste 320 bytes).

  5. Bring BBS back online.

Any PPE scripts that reference the new tokens will fail at runtime
under 15.3.  Recompile them without U_PERSONAL etc., or restore your
old 15.3 versions.

8.  KNOWN LIMITATIONS OF THIS PORT
═══════════════════════════════════════════════════════════════════════════════

Compared to what Clark shipped in 15.4b:

  - GETMSGHDR / SETMSGHDR return "" (function form) and MOVEMSG is a
    no-op (statement form).  Tokens, argument evaluation, and
    dispatch cases are all in place as of v0.024; what's still
    pending is the movemessage() / getmsghdr() / setmsghdr() helpers
    that touch the actual MSGS files.  Those helpers live in a
    separate translation unit that needs its own reverse engineering.
    Tracked as v0.025.

  - SHORTDESC(recnum) function form: currently ignores the recnum
    argument and reads from the current user.  Working for the common
    case (script asking about the caller); not working for cases
    where a PPL script wants to check ANOTHER user's setting.  The
    statement form SHORTDESC value works correctly since it only ever
    touches the current caller.

  - SETBANKVAL statement form works correctly — writes directly to
    the in-memory Account struct.  Persistence happens at next USERS
    file write, same as any other Account-PSA change.

  - The utility binaries (PCBSETUP, LOCAL, UUOUT, UUUTIL, UUXFER) are
    NOT rebuilt from source in this port because their source was
    packaged with a \PROJ\ path structure that requires makefile
    surgery before they'll build.  Use the pcb154b binaries for those
    tools — they're compatible with the schemas we've extended.

  - The 15.4b Local logon utility (LOCAL.EXE, ~768 KB code region)
    has not been sourced or reversed; use the shipped binary.

Nothing above prevents the BBS from RUNNING correctly.  These are
gaps in this port, not runtime bugs.

10.  MD5 CHALLENGE-RESPONSE HANDSHAKE (v0.025)
═══════════════════════════════════════════════════════════════════════════════

15.4 activates an authentication feature that was present but disabled in the
15.3 source: an MD5 challenge-response handshake sent before login by
terminal programs that support it.  Recovered from PCBOARDM.EXE 15.4b runtime
strings ("Watching for MD5 String", "MD5 String Received!") and traced back
to five `#if 0 && defined(CPU386) && defined(MULTIPORT) && ! defined(LIB)`
blocks in MAIN/SOURCE/MAIN/INKEY.C that v0.025 unwraps to
`#if defined(CPU386) && defined(MULTIPORT) && ! defined(LIB)`.

WHAT IT DOES
────────────
When a caller connects, PCBoard watches for a 34-byte sequence:

    < XX XX XX XX ... XX XX XX XX >
      1  2  3  4      29 30 31 32

where each XX is a hex digit (0-9, A-F).  The angle brackets frame a 128-bit
MD5 hash — the caller's terminal program has already computed
`MD5(secret + timestamp)` and sends the digest before the login prompt.

If the sequence is well-formed, PCBoard:

  a) Sets Md5Stage = MD5DONE
  b) Stores the hash in `ReceivedMd5String`
  c) Exposes it to DOOR programs via the environment variable
     `MD5LOGIN=<hash>` (see DOORS.C line 148, LOGIN.C line 819)

If any byte is not a hex digit, or the terminating `>` is missing, the
handshake aborts silently and PCBoard falls back to normal login.

HOW TO USE IT
─────────────
The handshake is passive — PCBoard doesn't validate the hash itself.
It captures the string and hands it to any door or PPL script that wants
to use it for verification.

Typical use case: an authenticated terminal program shares a secret with
your BBS's PPL script; the terminal sends `MD5(secret + $timestamp)` and
the script validates it against the same computation server-side.

Example PPL check inside a door script:

    STRING md5login
    LET md5login = GETENV("MD5LOGIN")
    IF (LEN(md5login) = 32) THEN
      ; Terminal authenticated via MD5 — skip password prompt
      GOTO fast_login
    ENDIF

INTERACTION WITH FIDO
─────────────────────
The MD5 watch runs in parallel with the WATCHFORFIDO logic.  If a Fido
`*` (EMSI) or `0xF1` (WAZOO) byte arrives first, PCBoard aborts the MD5
watch and enters Fido mode instead.  No conflict, no configuration
needed.

WHY IT WAS DISABLED IN 15.3
────────────────────────────
The 15.3 source shipped with the code fully written but wrapped in
`#if 0 && ...` blocks.  Best guess: Clark wanted the feature working for
15.4 release timing but didn't want it accidentally enabled in field
builds of 15.3.  v0.025 simply removes the `0 &&` guard.

13.  UUCP REJECTS FILTER (v0.026, source-side implementation pending)
═══════════════════════════════════════════════════════════════════════════════

WHATSNEW item #10 documents a REJECTS filter added to UUIN in 15.4 that
lets sysops bounce or silently drop UUCP mail from named senders.

RE evidence in UUIN.EXE 15.4b (file offsets):

    0x3d344  "REJECTS"       ← the filter config filename
    0x3d0f1  "bounce"
    0x3d0f5  "BOUNCE.TXT"    ← bounce message body template
    0x3d???  "Bounced Mail -> User Not Found"
    0x3d???  "Bounced Email -- %s (%s)"
    0x3d???  "User Not Found -- %s (%s)"

FILE FORMAT (per WHATSNEW)
──────────────────────────
Create a file named "REJECTS" (no extension) in your UUCP base path
(typically PCB\UUCP\).  ASCII text.  One entry per line:

    from_address, action_flag

Where `action_flag` is either `%` (bounce, i.e., return-to-sender via
BOUNCE.TXT) or absent (silent drop).

Maximum 16 entries.  Only e-mail can be bounced; Usenet articles can
only be dropped silently even if `%` is specified.

Example REJECTS file:

    annoying@bad.stor, %          this message will be bounced
    dah@news.bad,                 this message will be dropped silently
    spammer@bulk.mail, %          bounced
    quiet@ignore.me,              dropped

BOUNCE.TXT
──────────
Companion file, also in UUCP base path.  Contains the text of the
bounce message emitted when an entry with `%` matches.  Standard
@X-code substitution applies (%s for sender, etc.).  If BOUNCE.TXT
is missing, UUIN falls back to a default one-line message.

STATUS IN THIS PORT
───────────────────
LANDED (v0.027).  REJECTS.CPP and REJECTS.HPP are in
MAIN/SOURCE/UUCP/UUIN/ and wired into UUIN.CPP's mail and news
intake paths.  UUIN.MAK builds them alongside decodem.obj.

The parser reads the REJECTS file at UUIN startup, matches each
inbound message's From: address against the list, and either:
  - Silently drops the message (action absent), or
  - Sends a bounce reply via UUOUT using BOUNCE.TXT as the body
    template (action = %, e-mail only)

For news articles, both action forms result in a silent drop
(per WHATSNEW: "only email can be bounced").

QUICK-START FOR SYSOPS
──────────────────────
  1. Create the REJECTS file:

       cd C:\PCB\UUCP
       edit REJECTS

     Add one entry per line:

       spammer@bulk.mail, %
       @annoying.example,
       root@untrusted.host, %

  2. Optional: create BOUNCE.TXT in the same directory with your
     preferred bounce message text.  If missing, a compiled-in
     default is used.

  3. Restart UUIN.  It reads REJECTS at startup — if you edit the
     file mid-run, changes take effect on next run.

  4. Verify the filter loaded correctly by running UUIN with the
     -verbose flag (calls dumpRejects() to stdout).

  5. Test by sending yourself mail from an address matching one of
     your entries and confirming it's dropped/bounced.

MATCH SEMANTICS
───────────────
The address comparison is a case-insensitive SUBSTRING match, so:

  Entry             Matches from:
  ────────────────  ────────────────────────────────────────
  bad@example.com   bad@example.com only
  @spam.tld         anyone@spam.tld, other@spam.tld, ...
  @                 EVERYTHING (don't do this)

This lets sysops write short entries that match whole domains or
specific senders as needed.  Order in the file doesn't matter —
first match wins.  Blank lines and lines without a comma are
silently ignored.

LOGGING
───────
Every rejected message is logged to UUIN's log file with:
  "Bounced Email -- from@address (subject)"    (bounce action)
  "REJECTS: dropped mail from from@address"    (drop action)
  "REJECTS: dropped news from from@address"    (news, always drop)

Grep the log to see what was filtered:
  find "REJECTS" UUIN.LOG
  find "Bounced" UUIN.LOG

14.  TROUBLESHOOTING AND FAQ
═══════════════════════════════════════════════════════════════════════════════

SYMPTOM: Users complain they were prompted for gender/email/web on their
LAST login but the fields aren't stored.

  CAUSE:   PCBPERSONAL PSA not installed in USERS.INF.  The registration
           prompts fire before the PSA is available, so data is captured
           into memory but has no on-disk destination.

  FIX:     Run PCBSM → menu 7 → 3 → 9 (Personal Info Support).  Then
           re-prompt the user or edit their record manually via PCBSM
           menu 7 → 2 → their record → Personal Info.

SYMPTOM: PPE compiled with the new PPLC.EXE won't load on my other
network node.

  CAUSE:   Version mismatch.  Only nodes running the v0.025+ PCBOARDM
           can load 3.40-version PPE files (CUR_PPE_VER = 340 refuses
           older).  A 15.3 PCBOARDM sees the 3.40 header and refuses.

  FIX:    Upgrade all nodes to the v0.025+ PCBOARDM at once, OR keep
          15.3 PPE builds around and don't recompile scripts that
          need to run on mixed-version networks.

SYMPTOM: MD5 handshake doesn't fire — "Watching for MD5 String" never
appears.

  CAUSE 1: The build wasn't compiled with CPU386 + MULTIPORT + not
           LIB.  All three preprocessor conditions must be true (see
           v0.025 CHANGES entry).
  CAUSE 2: The Status.LoggingIn WATCHFORMD5 bit isn't set.  This is
           set by the login handshake — if you jump straight into
           the caller loop from a script, no MD5 watch.

  FIX:     Check your make output for -DCPU386 -DMULTIPORT and confirm
           LIB is NOT defined.  Check that your Status.LoggingIn init
           includes the WATCHFORMD5 flag (this happens automatically
           on new connection; only PPL scripts that override the login
           flow need to worry about it).

SYMPTOM: SETMSGHDR silently fails — the header change isn't persisted.

  CAUSE:   Message-base write requires the file to be openable in
           read/write mode.  If the MSGS file is locked by another
           node (e.g., someone reading in the same conference), the
           open() succeeds but writeHdr() silently fails.

  FIX:     Retry with a small delay in your script, or serialize your
           header edits (do them at maintenance time when no callers
           are online).  Alternatively, check the return value:
             INTEGER ok
             LET ok = SETMSGHDR(0, msg, 3, "New subject")
             IF (ok = 0) PRINTLN "Failed — try again later"

SYMPTOM: REJECTS file exists but nothing gets filtered.

  CAUSE 1: File missing the comma separator — lines must be
           `address, action` even for silent-drop (the comma is required).
  CAUSE 2: File in wrong location.  Must be in PcbData.uucpPath,
           typically C:\PCB\UUCP\.
  CAUSE 3: >16 entries.  Only the first 16 lines with commas are loaded.
  CAUSE 4: Case-sensitive comparison — the parser lowercases both
           sides so this should not happen; but if you edited the
           file with a tool that inserted BOM bytes or NULs, the
           first entry may have garbage prepended.

  FIX:     Run UUIN -verbose to see the dumpRejects() output.  It
           lists exactly which entries were parsed and their bounce
           flag.

SYMPTOM: U_EMAIL, U_GENDER etc. work in scripts but show as blank on
first read.

  CAUSE:   The PSA was installed AFTER these users registered.  Their
           on-disk record has zero-filled PSA data, which the runtime
           correctly shows as blank.

  FIX:     Prompt the user to fill in their profile, or write a PPL
           script that walks users and prompts them at next login.
           A migration door PPE is the usual approach.

SYMPTOM: The new PPL variables (U_GENDER etc.) show as blank on some
callers but not others.

  CAUSE:   The blank callers are guests, expired, or logged in under
           an alias.  When cSCRIPT::loadUser() populates ptrPersonal
           it uses the current user's record — anonymous / guest
           accounts don't have Personal PSA data.

  FIX:     Check U_ALIAS or U_SEC in your script and skip the
           personal-info branch for callers who shouldn't have it.

SYMPTOM: PCBSM's "Edit Personal Info" menu entry is greyed out.

  CAUSE:   PersonalSupport was FALSE when PCBSM started.  Either the
           PSA isn't installed, or PCBSM was launched before you
           installed it.

  FIX:     Restart PCBSM after installing the PSA.

15.  EXAMPLE PPL SCRIPTS
═══════════════════════════════════════════════════════════════════════════════

These are ready-to-compile scripts demonstrating each new 15.4 feature.
Save with a .PPS extension and compile with PPLC 3.40+.

Example 1 — Birthday greeter
─────────────────────────────
Greet users on their birthday when they log in.

    ; BDAYGRT.PPS — Birthday Greeter
    ; Runs from PCBTEXT record 87 (login banner)
    STRING  today, bd
    LET today = STRIP(DATE(),"/")           ; MMDDYY
    LET bd = U_BIRTHDATE
    IF (LEN(bd) = 6) THEN
      IF (LEFT(bd,4) = LEFT(today,4)) THEN
        PRINTLN "@X0EHappy Birthday, ",U_NAME(),"!  @X07"
        NEWLINE
      ENDIF
    ENDIF

Example 2 — Email harvester for sysop maintenance
──────────────────────────────────────────────────
Print a list of all users with a set email address.  Sysop-only.

    ; EMAILLST.PPS — dump users with email
    INTEGER rec, n
    STRING  em
    LET n = U_RECNUM()
    FOR rec = 1 TO n
      GETUSER
      LET em = U_EMAIL
      IF (LEN(em) > 0) THEN
        PRINTLN U_NAME()," <",em,">"
      ENDIF
      INC rec
    NEXT

Example 3 — Message header viewer
──────────────────────────────────
Show a specific message's header fields.

    ; MSGHDR.PPS
    STRING  input, s
    INTEGER conf
    DOUBLE  msg

    LET conf = CURCONF()
    PRINTLN "Enter message number:"
    INPUT "> ", input
    LET msg = TODREAL(input)

    PRINTLN "From:    ",GETMSGHDR(conf,msg,11)
    PRINTLN "To:      ",GETMSGHDR(conf,msg,7)
    PRINTLN "Subject: ",GETMSGHDR(conf,msg,12)
    PRINTLN "Date:    ",GETMSGHDR(conf,msg,5)
    PRINTLN "Status:  ",GETMSGHDR(conf,msg,1)

Example 4 — Rename messages sent to old sysop handle
─────────────────────────────────────────────────────
If your board changed sysop names, rewrite the To field on messages
addressed to the old name.

    ; RENAME.PPS — sysop-only maintenance script
    DOUBLE msg, lo, hi
    STRING to

    IF (U_SEC < 100) THEN
      PRINTLN "Sysop only."
      END
    ENDIF

    LET conf = CURCONF()
    LET lo = LOMSGNUM()
    LET hi = HIMSGNUM()
    FOR msg = lo TO hi
      LET to = GETMSGHDR(conf,msg,7)
      IF (RTRIM(to," ") = "OLD SYSOP") THEN
        SETMSGHDR(conf, msg, 1, "NEW SYSOP")   ' field 1 in SET = To
      ENDIF
    NEXT

Example 5 — Move stale messages to archive conference
──────────────────────────────────────────────────────
Move all messages older than 90 days into conference 99 (Archive).

    ; ARCHIVE.PPS — sysop maintenance
    INTEGER srcConf, archConf
    DOUBLE  msg, lo, hi
    STRING  dt
    LET srcConf = 1
    LET archConf = 99

    LET lo = LOMSGNUM()
    LET hi = HIMSGNUM()
    FOR msg = lo TO hi
      LET dt = GETMSGHDR(srcConf,msg,5)   ; MMDDYY
      IF (isolder(dt,90)) THEN            ; user helper function
        MOVEMSG archConf, msg, TRUE       ; TRUE = delete source
      ENDIF
    NEXT

Example 6 — Time Bank deposit
──────────────────────────────
Award the caller 30 minutes of time-bank credit.

    ; TIMEDEP.PPS — deposit 30 minutes into Time Bank
    DOUBLE curBal
    LET curBal = GETBANKBAL(3)         ; field 3 = Amount Saved (minutes)
    IF (curBal + 30 <= GETBANKBAL(5)) THEN   ; check against max
      SETBANKBAL 3, curBal + 30
      PRINTLN "@X0AAdded 30 minutes to your time bank. Balance: ",curBal+30
    ELSE
      PRINTLN "@X0CBank full - would exceed max stored amount."
    ENDIF

Example 7 — MD5LOGIN fast-path
───────────────────────────────
Skip password prompt for callers whose terminal sent a valid MD5.

    ; MD5FAST.PPS — called from BOARD.PPE or LOGIN.PPE
    STRING hash, computed
    LET hash = GETENV("MD5LOGIN")
    IF (LEN(hash) = 32) THEN
      ; caller's terminal computed MD5(secret + timestamp) — validate
      LET computed = COMPUTEMD5(U_PWD + TIMESTAMP())
      IF (hash = computed) THEN
        PRINTLN "@X0FTerminal authenticated via MD5.  Bypassing password."
        GOTO fast_logged_in
      ENDIF
    ENDIF
    ; fall through to normal password prompt
    ...
    :fast_logged_in

    MOVEMSG errors in 15.4b's PCBOARDM data section were confirmed as
    strings but their DISPLAY method (fastprint vs. printerr vs.
    logfile vs. something else) was not verified.

  - v0.024 SETBANKVAL / v0.021 GETBANKVAL Account-PSA writes.
    These were WRONG — Time Bank is a separate PSA per WHATSNEW.
    Fixed in v0.029: both dispatches now safely no-op.  If you were
    running v0.024–v0.028 with scripts calling SETBANKVAL, those
    scripts corrupted callers' Account PSA data.  This is a real bug
    and I apologize for shipping it uncorrected across four revisions.

                             runnable as written.

  - Troubleshooting FAQ symptoms are my guesses at what might go
    wrong.  Some (like MSGS file lock) are based on general knowledge

DOSBOX BUILD MACHINERY — GOTCHAS FOR REPRODUCERS
────────────────────────────────────────────────

Documented for anyone rebuilding this port:

  1. DOSBox's `>>` append-redirect silently drops output.  The log
     file comes out zero bytes.  Use single `>` truncate + separate
     accumulator files instead.

  2. DOSBox's `2>&1` stderr merge breaks the redirect parser entirely.
     Log comes out empty.  Drop `2>&1`; use single-stream `>` only.

  3. Borland MAKE 3.6 escapes `\b`, `\n`, `\t` as C-style escapes in
     shell-invoked commands.  A tlib line like:
         tlib LIB + $(OBJDIR)\bgetkey
     produces a literal 0x08 byte where the `\b` was, and TLIB rejects
     it with "unexpected char '\b'".  Workaround: write a TLIB response
     file (`+objname &` continuation-line format) and `cd` into OBJDIR
     first so no paths with `\b` appear on the command line.

  4. Hand-written makefiles need CRLF line endings, not LF.  Borland
     MAKE tolerates LF for parsing but escape-processing rules differ
     subtly.  Convert with `sed 's/$/\r/'`.

  5. .C vs .CPP matters for pascal linkage.  Borland's build config
     includes `-P` which forces C++ compilation of .c files.  C++
     with pascal linkage produces mangled exports (e.g.
     `@MD5STRING$QNUCIT1`).  For pascal functions called from other
     modules, use .CPP and `extern "C"` wrapping to get plain
     unmangled exports.

  6. The linker response file (e.g. `153/PCB_BC31.386`) is a separate
     hand-maintained file, NOT auto-generated from the makefile.  Any
     new .obj must be added to BOTH the .MAK OBJ list AND the .386
     response file, or the object gets built but never linked in.

  7. Environment variable BC31PATH must be set to `\B\C31` before
     calling bcdos.bat, or the compiler paths resolve incorrectly.
     Set it explicitly in your driver batch file.
